# 11 — Data and scenarios

## 1. Splits

Generated, never downloaded. Every split is a disjoint set of scene seeds, and the split is a pure
function of the seed:

| Split | Scene seeds | Purpose |
|---|---|---|
| train | 0 – 3,999 | fitting Stage A/B templates |
| calibration | 4,000 – 4,999 | fitting temperature, reliability, pair likelihoods, forward model, planner weight sweep, stopping thresholds |
| development | 5,000 – 5,999 | every number reported during development; threshold sensitivity |
| test | 10,000 – 10,399 | the confirmatory Gate E only |

The demo reduces counts (240 / 120 / 120 / 120) but keeps the seed ranges and the disjointness, so
demo and full runs differ only in N.

`verify` asserts:

- no seed appears in two splits;
- no fitted artifact's provenance names a calibration or test scene outside its allowed range;
- the test split was not touched by any `fit_*` function (checked against the artifact's recorded
  input hashes).

## 2. Class balance and scenario mix

Each split is balanced over the four causes by construction: a scene's cause is
`["defect", "reflection", "shadow", "none"][seed % 4]` for the core mix, with the scenario assigned by
`seed % 5` where applicable. The generator records the realised counts; the demo prints them and
Stage A asserts a maximum imbalance of 5 %.

Scenario mix in the test split: S1 40 %, S2 20 %, S3 20 %, S4 0 % (S4 is exercised separately and is
not in the primary endpoint), none-cause 20 %. The mix is fixed in the config, not in code.

## 3. Leakage control

The simulator makes leakage easy to introduce accidentally. Four rules:

1. **Scene-level splits.** Observations from one scene never cross splits, because a split is a seed
   range.
2. **No test-time fitting.** Temperature, thresholds, forward model and pair likelihoods are fitted on
   calibration only. `verify` fails if a fit artifact records a test scene.
3. **No ground-truth features.** `EvidenceBuilder` receives `Observation`, which has no cause; the
   verify command scans the serialized evidence for a `cause` key and fails if found.
4. **Policy-independent fit schedules.** Pair likelihoods are fitted on episodes that follow a fixed
   base → light → zoom schedule, not on trajectories generated by the policy being evaluated. If the
   policy chose the fitting schedule, the model would be tuned to its own choices.

## 4. The four scenarios

| ID | Share | Construction | Cause labels | Notes |
|---|---|---|---|---|
| S1 | 40 % | high-gloss plate, cause ∈ {defect, reflection} | 2 | the core ambiguity; light change decisive |
| S2 | 20 % | occluder over 12–25 % of the plate; cause ∈ {defect, reflection, none} | 3 | tests occlusion → debt, not absence |
| S3 | 20 % | cause ∈ {defect, shadow} | 2 | soft-vs-sharp; light change separates |
| S4 | separate | none → defect introduced after step 1 | 2 states | state-change contradiction; not in Gate E |
| — | 20 % | cause = none, no occluder | 1 | the null class, needed for calibration |

S1 is oversampled because it is the only scenario where the pair feature is decisive and therefore
the only one where the planner's choice matters most. This is a design decision that increases
statistical power for H1; it also means the headline error rate is not the error rate of a realistic
factory mix, which is stated in every report.

## 5. Real data (secondary, Gates C and D)

The simulator is not the world. The real-data check is specified now and executed after Gate C:

- **Dataset.** MVTec AD 2 is the intended target (eight industrial scenarios including lighting
  changes, reflective/transparent objects, overlaps and very small defects). Its reported difficulty
  (leading methods below 60 % AU-PRO in the 2026 evaluation cited by the vision memo) makes it a
  hard but appropriate transfer check.
- **What transfers.** The feature extractor (frozen), the temperature/reliability fitting procedure,
  and the *logic* of the ledger. The pair features require controlled re-observation, which MVTec AD 2
  provides only for its lighting-change subsets; scenes without paired observations cannot test H2/H4.
- **What does not transfer.** The simulator's exact feature distributions. The likelihood model must
  be refitted on real calibration scenes; a model refitted on real data is a different model, and its
  numbers are reported separately, never pooled with simulator numbers.
- **Claim level.** A real-data result is at most level 2 (feasibility) in v1 unless it was
  pre-registered separately.

The dataset citation is recorded in `docs/17_REFERENCES.md` as *user-supplied, unverified* until the
paper and dataset card are checked; this dossier does not assert the 60 % figure as established.

## 6. Data artifacts

| Artifact | Format | Content |
|---|---|---|
| `results/scenes.jsonl` | one line per scene | scene id, seed, cause, scenario, split |
| `results/episodes.jsonl` | one line per episode | actions, records, posteriors, decision, ground truth |
| `results/features.npz` | numpy | cached base-observation features for Stage A (optional) |
| `results/splits.json` | JSON | seed ranges, realised counts, hashes |
| `results/stage_*.json` | JSON | metrics per gate |

Images are **not** committed. The simulator regenerates any image from `(scene_id, seed, action)`, and
the record carries `image_sha256` so a regenerated image can be checked. This keeps the repository
small and makes the data a pure function of code + seeds, which is the stronger reproducibility
property.

## 7. Dataset versioning

`inspection-v1.0` fixes the renderer, the action space, the noise model and the ground-truth schema.
Any change to those is `inspection-v1.1` and invalidates comparisons across versions; every result
file stamps the version. Changes to N, seeds or scenario mix do not change the version and are recorded
in the config hash.

## 8. Known gaps

- No real images are used in v1; the transfer check is specified, not executed.
- No multi-object scenes; the simulator has one plate and one candidate anomaly.
- No temporal dynamics beyond the single S4 mutation.
- No domain randomisation beyond gloss, amplitude, position and orientation; textures are simple.
- The "none" class has no anomaly by construction, which makes its detection easier than in reality.
  This flatters Gate A's accuracy and is stated in `docs/19` when the number is reported.
